# knowledge.md — context-harness-mcp

> Durable decisions, constraints, patterns, and stack notes for this repo. Append a one-line bullet per durable item, tagged with the appropriate prefix. Do NOT delete entries — supersede them with a later entry referencing the original.

## Stack

- `[stack]` Go 1.22+, `github.com/mark3labs/mcp-go` (MCP framework), `github.com/jackc/pgx/v5` (Postgres driver) + `github.com/pgvector/pgvector-go` (pgvector type binding), `github.com/Anush008/fastembed-go` (ONNX runtime, `all-MiniLM-L6-v2`, 384 dims). Validation via `github.com/go-playground/validator/v10`. Logging via stdlib `log/slog` JSON handler.
- `[stack]` Migrations gestionadas por `github.com/pressly/goose/v3`. Go-native, single binary baked into el runtime stage del `Dockerfile`. Mismo `goose up` aplicado a Supabase desde dos puntos: el profile opcional `migrate` del docker-compose local (`docker compose --profile migrate run --rm migrate`) para devs, y el workflow `deploy.yml` (auto en push a main) para CI/CD. `supabase db push` deliberadamente NO se usa — aporta menos control de versionado que goose y duplicaría la ruta de migraciones.
- `[stack]` Supabase Free (500 MB DB, sin PITR, auto-pause tras 7 días de inactividad de DB) + Render Free (cold starts de 15 min de inactividad tolerados gracias al startup de 1-3 s del binario estático de Go). Solo se usan en Phase 2.
- `[stack]` MCP transport en producción: `streamable-http` (el reemplazo de SSE introducido por la revisión de la spec MCP de marzo 2025). Local-dev usa `stdio`. SSE es legacy y no se usa.
- `[stack]` Vector index: pgvector HNSW con `vector_cosine_ops`, defaults `m=16, ef_construction=64`. Coincide con la métrica `hnsw:space: "cosine"` del ChromaDB origen para preservar la vecindad semántica tras la migración.
- `[stack]` Scripts de migración en Python bajo `scripts/`, gestionados con `uv`. Reutilizan `claude-dev-team/knowledge-graph/migrate_knowledge.py`, `export.py`, `import.py`. NO forman parte del runtime del servidor.
- `[stack]` Build: multi-stage `Dockerfile` (`golang:1.22` → `debian:bookworm-slim`). Runtime stage incluye el shared library de ONNX en `/usr/local/lib` con `LD_LIBRARY_PATH` seteado, y el binario `goose` en `/usr/local/bin`. La misma imagen se usa en Phase 1 (docker-compose local) y Phase 2 (Render).
- `[stack]` Tests: stdlib `testing` + `github.com/stretchr/testify` + `github.com/testcontainers/testcontainers-go/modules/postgres` v0.35.0. Integration tests levantan `pgvector/pgvector:pg16` ephemeral aislado por test run vía testcontainers — no dependen del docker-compose ni de Supabase. Requiere Docker daemon corriendo en la máquina (dev o CI). `TestMain` aplica migraciones vía `goose.Up` library (mismo path que prod) y expone `NewTestPool(t)` + `CleanDB(t)` helpers.
- `[stack]` `github.com/zricethezav/gitleaks/v8` — usado como library (no CLI). Lazy-load en primer request post-cold-start para evitar penalty en boot. ~150 default rules + custom rules si emergen.

## Decisions

- `[decisión]` Costo mensual recurrente $0 — Render Free + Supabase Free. PITR reemplazado por un GitHub Action semanal de `pg_dump` cifrado (ventana de recuperación de 7 días). Auto-pause de Supabase Free mitigado por un GitHub Action cada 6 días que ejecuta `SELECT 1`. Trade-off aceptado vs la alternativa de pago, a cambio de cold starts y operación manual de backups/healthchecks.
- `[decisión]` Stack del servidor en Go (`mcp-go` + `pgx/v5` + `fastembed-go`) para que el cold-start de Render Free se mantenga en ≤3 s. Python sería 15-30 s y haría inviable el Free tier. Se aceptó la no-reutilización con `claude-dev-team/knowledge-graph/server.py` (Python) — el costo de reescritura (~700-800 LoC) se paga una sola vez y se recupera en hosting.
- `[decisión]` Deploy en dos fases secuenciales contra la misma imagen Docker y la **misma Supabase Free**. Phase 1 = `docker compose up` local (solo el servicio mcp) conectado a Supabase vía `SUPABASE_DB_URL`. Phase 2 = la misma imagen pusheada a Render Free apuntando a la misma Supabase. Eliminado el Postgres local del compose por simplicidad (un solo DB target, sin dual-config). Trade-off aceptado: Phase 1 pierde el rol de "fallback operacional" — si Supabase Free pausa, el local también queda muerto. Roles conservados: primer hito de deploy con validación E2E contra la cloud DB real, dev environment con paridad de DB exacta, base natural para futuro self-hosting.
- `[decisión]` Sin auth en el MCP endpoint — URL pública, trade-off aceptado deliberadamente por el usuario (ver `session-docs/initial-design/01-architecture.md` §Risk Register). Mitigaciones: subdomain de Render largo y aleatorio, Content Filter de tres capas server-side (syntactic / secrets / taxonomy) contra `kg-content-policy.md`, rate limiting por IP, soft-delete (cada herramienta `delete_*` setea `deleted_at`, jamás hace `DROP`), `pg_dump` semanal cifrado off-Supabase.
- `[decisión]` Schema drop-in compatible con `claude-dev-team/knowledge-graph` (ChromaDB) — tres tablas (`entities`, `observations`, `relations`) + columna `vector(384)` en `observations`. Sin `tenant_id` (single-tenant v1; YAGNI). Una migración futura para agregar multi-tenancy es un cambio aditivo de una sola PR.
- `[decisión]` Embedding model locked a `all-MiniLM-L6-v2` (384 dims) hasta que la migración desde ChromaDB esté completa. Cambiar el modelo después requiere un re-embed total del KG. Post-cutover este lock puede reconsiderarse.
- `[decisión]` Migración desde ChromaDB es one-shot (export → import + flag day), no dual-write. ChromaDB local se mantiene como cold backup por 30 días post-cutover.
- `[decisión]` Transporte MCP de producción = `streamable-http`, no SSE — SSE es de la era 2024 reemplazada por streamable-http en la revisión de spec MCP de marzo 2025; `mcp-go` lo expone vía `server.NewStreamableHttpServer`.
- `[decisión]` Render Free deploy se hace vía `Dockerfile` (no native Go builder) porque `fastembed-go` requiere el shared library de ONNX que el builder nativo no provee.
- `[decisión]` ONNX session se carga lazy en el primer request de embedding (vía `sync.Once`), no eagerly al startup, para mantener el cold-start del servidor en ≤3 s para tools no-embedding (`read_graph`, `open_nodes`).

## Restrictions

- `[restricción]` No personal data, no tokens, no client/stakeholder data, no absolute Windows/WSL paths con user names en cualquier entidad u observación. Política heredada de `claude-dev-team/docs/kg-content-policy.md` y enforced server-side por el Content Filter (capa 3) antes de cada write.
- `[restricción]` Entity types son un enum cerrado de 9: `pattern`, `error`, `constraint`, `decision`, `tool-gotcha`, `process-insight`, `project`, `service`, `stack-profile`. Relation types son un enum cerrado de 5: `relates_to`, `belongs-to`, `calls`, `uses-stack`, `depends-on`. Agregar un tipo nuevo requiere actualizar `kg-content-policy.md` upstream y el `check` constraint en `migrations/`.
- `[restricción]` Cada observation pasa por 3 capas server-side antes de cualquier INSERT: (1) syntactic — 5000 char cap + 50 KB call cap + junk-pattern denylist curada in-code; (2) secrets scan vía gitleaks-as-library + regex inline fallback (AWS, GitHub, Anthropic, OpenAI, Stripe, RSA, JWT); (3) `kg-content-policy.md` taxonomy. Cualquier rechazo aborta el call completo (atomicidad — o se guarda todo o no se guarda nada).
- `[restricción]` Error responses del MCP usan códigos estables: `policy/size-exceeded`, `policy/junk-pattern`, `policy/secret-detected`, `policy/taxonomy-violation`. El `message` va en español para que Claude lo surfaceé al usuario sin re-traducción; incluye `layer` y `rejected_observation_index` cuando aplica.
- `[restricción]` Todas las deletes son soft (`deleted_at = now()`). Ninguna sentencia `DELETE` en ninguna implementación de tool. Cleanup duro es operador-only vía el SQL editor de Supabase Studio y está fuera del scope de la API MCP.
- `[restricción]` Contrato JSON de export/import preservado 1:1 desde `claude-dev-team/knowledge-graph/export.py` / `import.py` para que los archivos en `shared-knowledge/` se mantengan portables entre ambos backends durante coexistence.
- `[restricción]` Server binary single-static (con CGO habilitado para los bindings ONNX). Tamaño realizado de la imagen Docker en PR-6: ~413 MB virtual / ~138 MB on-disk / ~80 MB compressed-push — bien dentro del límite de 500 MB del Render Free slug. Breakdown real: base debian-slim ~80 MB + ONNX runtime libs ~150 MB + server (CGO + stripped) ~40 MB + modelo all-MiniLM-L6-v2 ~90 MB + goose (postgres-only, stripped) ~13 MB. El target original de ≤250 MB era infeasible con esta combinación; supersede ese número con esta entrada.
- `[restricción]` Modelo `all-MiniLM-L6-v2` baked en `/local_cache/fast-all-MiniLM-L6-v2/` durante el build del Dockerfile. La URL default de fastembed-go (`storage.googleapis.com/qdrant-fastembed/fast-all-MiniLM-L6-v2.tar.gz`) retorna 403 desde ~2026-05; el archive `sentence-transformers-all-MiniLM-L6-v2.tar.gz` en el mismo bucket sigue público y produce los mismos bytes ONNX. Dos symlinks dentro del image cierran gaps de naming de fastembed-go v1.0.0: `model_optimized.onnx → model.onnx` y `onnxruntime.so → libonnxruntime.so`. Si la URL alternativa también cae, fallback plan = bundlear el modelo directo desde Hugging Face (`sentence-transformers/all-MiniLM-L6-v2`) durante el build, evitando GCS por completo.
- `[restricción]` Scripts de migración en Python bajo `scripts/` — hybrid codebase deliberado para reutilizar `claude-dev-team/knowledge-graph/migrate_knowledge.py`. NO forman parte del runtime; ni Phase 1 (docker-compose) ni Phase 2 (Render) necesitan Python.
- `[restricción]` GitHub secrets requeridos para CD: `DATABASE_URL` (deploy + pg_dump + keepalive; `SUPABASE_DB_URL` aceptado como fallback deprecated por una release), `RENDER_DEPLOY_HOOK_URL` (deploy), `DUMP_PASSPHRASE` (pg_dump). `SUPABASE_ACCESS_TOKEN` — opcional, reservado para integración futura con Supabase CLI; ningún workflow actual lo consume. Los tres workflows activos tienen un guard step que exits 0 limpiamente si sus secrets están ausentes (emiten `::warning::` en el log).
- `[restricción]` Write tools (`create_entities`, `add_observations`, `create_relations`) rate-limited a 10 escrituras por 10 segundos por IP cliente (token bucket, burst 10, refill 1/s). Reads (`search_nodes`, `open_nodes`, `read_graph`) y deletes sin límite. IP leída desde `X-Forwarded-For` (Render pasa el IP real ahí); fallback a `RemoteAddr`. En transporte stdio no hay IP → no hay rate limit. Error code: `policy/rate-limited`.
- `[restricción]` Modo de detección de secretos configurable via `SECRET_MODE`: `reject` (default, aborta el call) o `redact` (reemplaza el span con `[REDACTED]` y deja continuar el call). Cualquier otro valor produce startup error (fail-fast, sin fallback silencioso). Implementado en `internal/validate/secrets.go` + `mode.go`; setter `SetSecretMode` para tests.
- `[restricción]` Junk-pattern denylist (capa 1 del Content Filter) vive en `internal/validate/denylist.go` como tabla in-code. Expandirla es una PR change con unit test, nunca env-var; un env-var permitiría que un deploy mal configurado relaje silenciosamente el filtro.
- `[restricción]` Misma imagen Docker para Phase 1 (docker-compose local) y Phase 2 (Render). Cualquier diferencia entre los dos targets debe vivir exclusivamente en variables de entorno (DB URL, log level, embedding model path opcional), nunca en build artifacts diferentes. Drift de build entre fases es un bug, no un feature.
- `[restricción]` `DATABASE_URL` es env var **requerida** en `docker-compose.yml` y en `cmd/server/main.go` (falla fast si no está seteada). `SUPABASE_DB_URL` se acepta como fallback deprecated con warning en stderr por una release; se elimina en v2.0. `.env.example` documenta el shape de la URL. El servidor usa pgx + pgvector — funciona con cualquier Postgres + pgvector, no específicamente Supabase; `DATABASE_URL` es el nombre estándar de la industria (Railway, Render, Fly, Heroku lo auto-populan).

- `[decisión]` `SUPABASE_DB_URL` renombrada a `DATABASE_URL` — el servidor usa pgx + pgvector y funciona con cualquier Postgres + pgvector (Supabase, Neon, AWS RDS, self-hosted, Docker). El nombre anterior implicaba vendor lock-in inexistente. `DATABASE_URL` es el estándar de la industria (Heroku/Render/Fly/Railway lo auto-populan al provisionar Postgres). Backward-compat: `SUPABASE_DB_URL` se acepta como fallback deprecated por una release con warning en stderr. Se elimina en v2.0.

## Patterns

- `[patrón]` Las signatures de las herramientas y los shapes JSON de retorno son byte-for-byte compatibles con `claude-dev-team/knowledge-graph/server.py` — los prompts del orquestador dependen de este contrato. Agregar campos nuevos está permitido; remover o renombrar existentes es un breaking change.
- `[patrón]` Content Filter como capas ordenadas con fail-fast — la primera capa que rechaza corta el flujo. Cada capa es testeable en aislamiento (un archivo Go por capa en `internal/validate/`, un test file por capa, golden files por error code).
- `[patrón]` Cada herramienta que escribe corre el payload por `internal/validate/Run` primero. Rejects de validación retornan un error MCP estructurado; no hay writes parciales — el `pgx.Tx` se abre sólo después de que el validator retorna `nil`.
- `[patrón]` Todo SQL está parametrizado vía `pgx` con `$1, $2, ...`. No string interpolation, no `fmt.Sprintf` dentro de SQL, jamás — incluso junto al validator (defense in depth).
- `[patrón]` PR splits entre servicios usan base PR + cleanup PR con cross-references bidireccionales (`Base PR:` / `Cleanup PR:` en `02-task-list.md`). Misma convención que `claude-dev-team`.
- `[patrón]` Self-describing task-list — cada PR lleva `Status:` field + AC checkbox mirror, visible sin cross-referenciar otros docs.
- `[patrón]` Migraciones son forward-only y aditivas en producción. `goose Down` annotations existen para dev/CI (`goose reset` entre tests) pero NO se invocan en prod. Cambios de schema en prod van: add column → backfill → switch reads → drop old column en un release posterior. Nunca editar una migración después de shipped a prod.
- `[patrón]` Embedding pipeline computa un vector por fila de observation (no por entity). `search_nodes` agrega por entity vía `min(distance)` para matchear la API surface a nivel entity.
- `[patrón]` ONNX session inicializada lazily vía `sync.Once` en el primer request de embedding. Tools que no embeden (`read_graph`, `open_nodes`) no pagan el costo de carga del modelo. Misma estrategia aplicada al gitleaks detector — lazy `sync.Once` en el primer write request post-cold-start.
- `[patrón]` Free-tier op model = weekly `pg_dump` cifrado (rollback window de 7 días) + 6-day `SELECT 1` keepalive cron (prevent auto-pause). Ambos como GitHub Actions schedules; runbook de rotación de secrets en `docs/cutover-playbook.md`.
- `[patrón]` Secrets scanning defensa-en-profundidad: gitleaks como library para coverage amplia (~150 reglas mantenidas por la comunidad) + regex inline fallback siempre activo para las 7 familias más críticas (AWS / GitHub / Anthropic / OpenAI / Stripe / RSA / JWT). Una falla o gap en gitleaks no abre un hueco en las familias high-impact.
- `[patrón]` Phased deploy — primer hito = Docker local con docker-compose (solo el servicio mcp) contra Supabase Free; segundo hito = Render cloud reusando la misma imagen contra la misma Supabase. Las migraciones SQL en `migrations/` son la única fuente de verdad del schema y se aplican a Supabase desde dos puntos: el profile opcional `migrate` del docker-compose (manual, dev local) y el workflow `deploy.yml` (auto, push a main).
- `[patrón]` Docker local stack cumple tres roles concurrentes: (1) primer hito de deployment con validación E2E contra la Supabase real antes de la PR de Render, (2) dev environment para iterar rápido (sin esperar rebuilds de Render), (3) base natural para futuro self-hosting en Coolify / Dokku / server propio. El cuarto rol original ("fallback operacional") se eliminó al remover el Postgres local del compose. La paridad dev/CI vive ahora en testcontainers (mismo binario Go, mismo postgres+pgvector ephemeral), no en el compose.
- `[patrón]` El cutover playbook vive en `docs/cutover-playbook.md` (committed al repo), no en session-docs, porque los operadores en flag day pueden no tener session-docs disponibles.
- `[decisión]` Delete tools (`delete_entities`, `delete_observations`, `delete_relations`) removidos del MCP public surface en PR3 — el endpoint MCP es público y sin auth, por lo que exponer destructive ops sin access controls crea un vector de borrado masivo no autenticado. Las funciones de soft-delete permanecen como store-level API (admin-script only, no MCP tool); operadores acceden via SQL directo o Supabase Studio.
- `[restricción]` Vocabulario de grafo adoptado globalmente en PR3: `entity`→`node`, `entityType`→`nodeType`, `entity_id`→`node_id`, tabla `entities`→`nodes`, archivo `entities.go`→`nodes.go` (en store/ y mcp/), JSON keys `created_entities`→`created_nodes`, `entity_count`→`node_count`, `rejected_entity_index`→`rejected_node_index`. Los 9 valores del enum (`pattern`, `service`, etc.) y el schema de `relations` no cambian. Cualquier re-uso de "entity" en nuevo código es un bug.

- `[decisión]` Auth en MCP endpoint vía Supabase Auth + JWT HS256 server-issued (v0.2.0 Phase 0). Supersede de la decisión "sin auth" porque el threat model cambió a uso compartido por equipo. Mecanismo: magic link → callback HTML → /auth/exchange (validation via GET /auth/v1/user, algorithm-agnostic) → MCP JWT 1y → middleware HS256 + revocation cache (TTL 1h + cache-aside via Database Webhook). Alternatives rejected: Auth0 (vendor extra), per-user keys (no SSO), Cloudflare Access (conflicto con free tier), two-secret rotation slot (complexity sin valor). Ver `session-docs/v0.2.0-team-features/01-architecture.md`.

- `[restricción]` MCP_AUTH env var = closed enum {none, enabled}. Garbage value → server falla fast en boot.
- `[restricción]` MCP_JWT_SECRET = single slot (no _OLD). Rotation = nuclear: todos los users re-auth via magic link. Cadencia anual.
- `[restricción]` SUPABASE_WEBHOOK_SECRET via header X-Webhook-Secret (NO Authorization — Supabase bug #38848 lo dropea). Verificación constant-time con hmac.Equal.
- `[restricción]` MCP_PUBLIC_URL usado para construir auth_login_url en error responses (fallback a r.Host).

- `[patrón]` Cache-aside revocation: LRU cache TTL 1h sobre users.revoked_at + Invalidate(sub) llamado por webhook handler → revocation latency E2E ≤2s en lugar de ≤1h. Sin webhook (fallback cron 6h): ≤7h worst case.
- `[patrón]` Structured auth error JSON shape: {code: "auth/X", message: <Spanish>, auth_login_url: <url|absent>, layer: "auth"}. auth_login_url presente para 4 re-auth codes; ausente para webhook-invalid-signature. Mensajes en español.

## Platform-agnostic refactor (refactor/platform-agnostic)

> These bullets supersede the Render/ChromaDB-locked entries above. The originals are preserved for historical record per the append-only convention.

- `[decisión]` Hosting platform-agnostic — supersede de "Supabase Free (500 MB DB...) + Render Free" (Stack §3) y "Costo mensual recurrente $0 — Render Free + Supabase Free" (Decisions §1) y "Deploy en dos fases secuenciales... Phase 1 = docker compose... Phase 2 = la misma imagen pusheada a Render Free" (Decisions §3) y "Render Free deploy se hace vía Dockerfile" (Decisions §9). El servidor se deploya a cualquier container host (Railway, Render, Fly, Coolify, self-hosted Docker, VPS propio, …) contra cualquier Postgres 16+ con pgvector (Supabase, Neon, Railway Postgres, AWS RDS, self-hosted, …). El repo no endorse un host sobre otro; `docs/deployment.md` documenta principios + ejemplos equally-weighted por plataforma. El costo $0 sigue siendo alcanzable con free tiers (Railway, Render, Fly, Supabase, Neon, …) pero no es la única configuración soportada.
- `[decisión]` Dos modos de deployment equally first-class — supersede de la framing "Phase 1 → Phase 2" (Decisions §3, Patterns §"Phased deploy"). **Local mode**: `docker compose up` con default `MCP_AUTH=none` (sin bearer), para single-developer / dev-machine / entornos fully-trusted. **Cloud/shared mode**: la misma imagen en cualquier container host con `MCP_AUTH=enabled` + JWT bearer en `~/.claude.json`, para memoria compartida de equipo o cualquier deploy expuesto más allá de localhost. La imagen es byte-identical; las diferencias viven exclusivamente en env vars.
- `[decisión]` Producto standalone — supersede del positioning de Schema/migración "drop-in compatible con claude-dev-team/knowledge-graph (ChromaDB)" / "Migración desde ChromaDB es one-shot" / "Embedding model locked... hasta que la migración desde ChromaDB esté completa" (Decisions §5–§7). `context-harness-mcp` ya no se posiciona como reemplazo de la implementación Python+ChromaDB de `claude-dev-team` — es el servidor MCP de memoria, standalone. La compatibilidad del schema y de los JSON wire shapes con esa implementación previa se conserva como hecho histórico (mismas 3 tablas, mismos field names) pero no es un selling point ni un constraint para evolución futura. El embedding model lock a `all-MiniLM-L6-v2` puede reconsiderarse cuando el costo de re-embed sea justificable.
- `[decisión]` `docs/cutover-playbook.md` eliminado — supersede del Pattern §"El cutover playbook vive en docs/cutover-playbook.md". Era el runbook one-shot de migración ChromaDB → Postgres; ningún nuevo deployer migra desde ChromaDB (instalan fresh). Las referencias cruzadas en `docs/deployment.md` y `docs/local-stack.md` fueron removidas. Procedimientos de recovery que vivían en ese doc (rollback criteria, secret rotation, emergency local fallback) migrados a `docs/deployment.md §Recovery from a backup` y `docs/local-stack.md §Emergency fallback`.
- `[stack]` Hosting target = cualquier container host con soporte para `Dockerfile` y healthcheck HTTP. Ejemplos validados: Railway, Render, Fly.io, Coolify, self-hosted Docker en VPS. La GitHub Action `deploy.yml` ahora lee `DEPLOY_HOOK_URL` (con `RENDER_DEPLOY_HOOK_URL` como fallback deprecated por una release) para soportar cualquier host que exponga una URL de webhook de deploy; plataformas que deployan en `git push` nativamente pueden skipear el paso.
- `[restricción]` `docs/deployment.md` rewriteado como guía genérica (principios + ejemplos equally-weighted por plataforma). El repo no endorse Render ni ningún host específico — la elección queda al operador según presupuesto, región, y comodidad operacional.

## v0.4.0 — Project scoping + conflict detection

- `[patrón]` Project scoping: tools accept optional `project` field; default `'global'`; reads without filter return all projects (back-compat with pre-v0.4.0 callers). v0.4.0.
- `[patrón]` Project naming convention: `^[a-z]([a-z0-9-]{0,62}[a-z0-9])?$`. Suggested convention: use the bare repo name (`zippy-backoffice`), lowercase kebab-case mandatory. v0.4.0.
- `[decisión]` Relation taxonomy expanded from 5 to 7: added `supersedes` (directional override, new → old) and `conflicts_with` (descriptive contradiction). Neither filters reads automatically — both are descriptive-only. v0.4.0.
- `[restricción]` Cross-project relations rejected server-side (`policy/cross-project-relation`). `relations.project_id` is denormalized for filter speed; consistency enforced at write time. v0.4.0.
- `[patrón]` `supersedes` and `conflicts_with` are descriptive-only relations. Neither filters reads automatically. To hide the OLD node after `mark_superseded(A → B)`, use `archive_old_observations: true` which soft-deletes the old node's observations (`deleted_at`). There is no read-time filter on `supersedes` or `conflicts_with`. v0.4.0.
- `[patrón]` `find_conflicts` uses loop-N-queries strategy (one pgvector query per target observation, client-side aggregation) instead of CROSS JOIN. Optimal for N≤10 observations per node and preserves HNSW efficiency. v0.4.0.

## v0.5.0 — Sessions

- `[patrón]` Sessions are tags, not security boundaries. Any caller can call `session_end` / `session_summary` on any session — same trust model as `project_id` (single-deployment trust). v0.5.0.
- `[patrón]` Cross-project sessions are allowed. `sessions.project_id` is denormalized at `session_start` time for filter speed; it is informational only and does not constrain which projects' nodes can attach to the session. v0.5.0.
- `[decisión]` `session_summary` includes soft-deleted nodes for audit completeness — callers get the full record of what the session created, not just what is currently active. v0.5.0.
- `[restricción]` `create_nodes` with a `session_id` whose `ended_at IS NOT NULL` is rejected with `policy/session-already-ended`. Pre-Phase-4 nodes (no `session_id`) and calls without `session_id` continue to work unchanged. v0.5.0.
